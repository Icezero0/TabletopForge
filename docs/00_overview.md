# 2 产品概述

TabletopForge 起步于 TRPG / DND 跑团场景，目前已引入房间类型 `Room.type`，支持按房间类型加载不同游戏模式。当前主要可用模式为 DND5E，ThunderStone 为原型与资产整理阶段。

系统以“房间”为核心协作空间。用户可以创建房间、加入房间，并在房间内完成角色卡管理、地图布置、Token 操作、普通聊天、角色扮演消息、骰子判定、操作日志记录与实时状态同步。

系统以房间为协作边界。成员、权限、邀请、基础 WebSocket 等属于房间基础层；DND5E 桌面、ThunderStone DBG 牌区等属于具体游戏模式。

---

# 3 产品目标

TabletopForge 的核心目标是：

1. 替代分散的角色卡文档与聊天记录，提供统一的跑团工作台。
2. 支持多人在同一房间中进行地图、角色、消息和状态协作。
3. 通过角色卡与状态追踪降低 HP、资源、法术位、状态效果等内容的维护成本。
4. 通过地图桌面与 Token 系统提供轻量在线战斗场景支持。
5. 通过 RP 消息与操作日志沉淀可回溯的跑团记录。
6. 通过 WebSocket 保证房间内关键状态实时同步。

# 5 系统总体架构

系统采用前后端分离架构。

```text
Frontend
  ├─ HTTP API       -> Backend
  └─ WebSocket      -> Realtime Service

Backend
  ├─ Auth / Users
  ├─ Rooms / Members / Permissions / Room Modes
  ├─ Messages
  ├─ Characters / Character States
  ├─ DND5E Tabletop / Scenes / Maps / Tokens / Assets
  ├─ Dice / Combat / Fog / Music
  ├─ ThunderStone Prototype / Card Assets
  └─ Realtime
```

后端采用模块化单体架构。前端通过 HTTP API 进行持久化业务操作，通过 WebSocket 接收房间内实时事件。

# 7 身份模型总览

系统采用三层身份模型：

```text
site_role：站点级身份
room_role：房间级身份
game_role：游戏级身份
```

三者互相独立，不做隐式绑定。

- `site_role` 用于站点级管理，例如反馈查看、站点角色设置。
- `room_role` 用于房间治理，例如入房审批、成员管理、房间信息维护。
- `game_role` 用于游戏内操作，例如切换地图、移动 Token、修改角色状态、暗骰。

当前后端已实现：`site_role`、`room_role`、`game_role`（`GM` | `PL` | `OB`）。Tabletop 权限见 [`08_permission_design.md`](08_permission_design.md) §6.4。

# 8 房间页面总览

房间页面是系统主要业务页面。

跑团主界面以 **地图视窗** 为核心，分区如下（详见 [`03_frontend_design.md`](03_frontend_design.md) §4.2）：

1. **顶栏工具** — 手型、绘制、测距、Pointer  
2. **左侧** — 房间管理、角色列表、素材面板  
3. **中央 MapViewport** — 地图、网格、Token、绘制  
4. **底部** — 战斗先攻轴  
5. **左下** — 会话面板（聊天 / 掷骰日志 / 冒险日志占位）  
6. **右侧** — 单槽信息查看 + 个人备忘录（按房间、仅自己可见）

```text
RoomPage
├── TopToolBar
├── LeftDock（房间管理 + 角色列表 + 素材）
├── MapViewport
├── CombatPanel
├── SessionPanel
├── RightInspector（InfoPanel + PersonalMemo）
```

掷骰日志已并入会话面板；冒险日志目前为占位，后续再实现结构化内容。

# 9 通信原则

系统存在两类通信方式：

1. HTTP API  
   用于需要持久化、权限校验和明确响应结果的操作。

2. WebSocket  
   用于房间内实时事件同步。

原则：

- HTTP API 负责权威状态写入。
- WebSocket 负责广播服务端确认后的结果事件。
- 前端可以进行乐观更新，但最终状态应以后端返回或广播为准。
- 关键状态变化必须写入操作日志。

# 11 系统设计原则

1. 以房间为核心组织系统结构。
2. 以服务端数据作为权威状态。
3. HTTP 负责持久化业务操作，WebSocket 负责实时同步。
4. 权限设计分层，避免站点、房间、游戏权限混用。
5. 业务模块边界清晰，避免将规则、地图、聊天、日志逻辑混杂。
6. 角色状态变化必须可追溯。
7. 初始版本优先解决实际跑团痛点，避免过早实现重型 VTT 功能。
8. DND5E 优先落地，但保留规则集扩展能力。
